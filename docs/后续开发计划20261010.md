## 二之二、部署待办（2026-10-12 记录，本轮**只记录不修**）

> **为什么只记录**：2026-10-12 决定部署位置暂不定（"先不定，本地能跑通就行"），
> 所以本轮**没有动** `docker/` 与 `deploy/` 下任何文件 —— 改了也无从验证。
> 但下面这些都是**已查实的**缺陷，写在这里避免下次重新调查一遍。
> 等确定部署机器后，逐条核对再动手。

### 1. 🔴 缺 `.dockerignore` —— 构建镜像会把真实密钥打进镜像层

已确认仓库根目录**没有** `.dockerignore`，而 `docker/Dockerfile:33` 是 `COPY . .`。
于是构建时会把根目录 `.env`（真实 API 密钥）和 `data/sessions/default.json`（79 KB 会话）
一起打进镜像层 —— **镜像一分发出去就等于泄露密钥**。

**修法**：新建根目录 `.dockerignore`，至少排除 `.env`、`.env.*`、`data/`、`logs/`、
`__pycache__/`、`.git/`、`*.log`、`tests/`。
**验收**：构建后 `docker run --rm <img> ls -a /app` 里不应出现 `.env`。

### 2. `docker-compose.yml` 强制要求部署方提供密钥，与"每人自持"冲突

`docker/docker-compose.yml:21` 写的是 `LLM_API_KEY=${LLM_API_KEY:?...}` ——
`?` 意味着**不提供就直接报错起不来**。但现在的设计是使用者各自在网页里填自己的密钥，
部署方根本不需要有密钥。**改成可选**：`${LLM_API_KEY:-}`。

### 3. 接口端口：建议不加第二个公网端口，用 nginx 按路径分流

`docker-compose.yml` 只映射 7860、`Dockerfile` 只 `EXPOSE 7860`。
接口（8000）对外时，**建议不新开端口**，而让 nginx 在同一个 443 上分流：
`/api/` → `127.0.0.1:8000`，`/` → `127.0.0.1:7860`。防火墙只开 22/80/443。

### 4. `deploy/deploy.sh` 读不到根目录 `.env`

`deploy/deploy.sh:61,68,70` 用的是 `-f docker/docker-compose.yml`，
而 Compose v2 的项目目录默认取 **compose 文件所在目录**（即 `docker/`），
根目录的 `.env` 不会被读取 → `${LLM_PROVIDER}` 等插值落到默认值，
第 2 条那个 `${LLM_API_KEY:?}` 还会直接报错。
**修法**：这些命令加 `--env-file .env`（或 `--project-directory .`）。**需实测确认 Compose 版本行为**。

### 5. nginx 的读超时小于 mf6 的运行超时

`deploy/nginx.conf` 的 `proxy_read_timeout 600s`，而 `model_builder.py:396` 里
mf6 子进程的 `timeout=3600s`。一次长算会被 nginx 掐断 ——
**这正是接口必须做成"后台任务 + 轮询"而不是同步阻塞的硬理由**。

### 6. 容器里的 mf6 版本与本地不一致

`docker/Dockerfile` 装的是 `MODFLOW_VERSION=6.4.4`，本机实测跑的是 **6.3.0**。
版本不同，容器里的行为未必与本地回归结果一致 → 部署时必须**重跑一遍**验证套件，
不能拿本地的绿勾当数。另 `Dockerfile:16-24` 装的 `libgdal-dev gdal-bin` 可能多余
（`geopandas>=0.14` 自带 GDAL wheel），需实测确认后再删。

### 7. 上传的 SHP 不在数据卷里

`docker-compose.yml` 的 `volumes: model_data:/app/data`，但用户上传的文件落在
Gradio 临时目录（`%TEMP%/gradio/...`），**不在 `/app/data` 下**，容器重启即失效。
影响范围有限：只影响 `source_zone.py` 里"按 SHP 文件名再找一次"的分支；
IR 里已物化的 `grid_indices` 不受影响。要么把上传目录也挂卷，要么在文档里写明。

### 8. 其它

- `requirements.txt` 的 `gradio>=4.20.0` **无上界**，本机实跑 6.18.0 —— 镜像可能装到
  不同大版本。建议收紧上界，或至少把"实测过的版本"写进文档。
- `deploy/nginx.conf` 的 Basic Auth 是注释状态（第 39-41 行）。按"每人自持密钥"的设计
  不做访问控制也说得通，但**要在文档里写明如何开启**。
- `Dockerfile` 无 `HEALTHCHECK`；`deploy/` 整套脚本自 2026-06-15 起未经验证。
- Docker 基础镜像是 `python:3.13-slim`，本机跑的是 3.11/3.12 —— 需确认
  gradio 6.18 + flopy 在该版本下全绿。

## 五、未修完的根因（2026-10-10 新识别）

> 本轮第 2 项只做到了"让用户看得见"，根因未除。以下是查证后确认仍然存在的两条。

### 5.1 IR 会在多轮提示词之间残留旧值

**现象**：用户改过提示词（`al` 从 40 m 改成 20 m、单层改成两层），但 IR 里 `al` 停在 **40**、
`trpt` 停在 **0.1**（新提示词写的是 0.2），且都标着 `"source": "user_input"`。
`porosity` 则被压成单值 0.2，两层信息丢失。

**位置**：抽取链路，`app/llm_agent/intent_parser.py` / `dialogue_manager.py`

**影响**：用户以为改一版提示词就能换一版参数，实际拿到的是**新旧混合**。
本轮加的参数溯源行能让用户**发现**，但不能**阻止**。

**待定**：这是"增量更新 IR"设计的固有代价（保留用户已确认的参数），还是缺陷？
动工前要先确认产品意图 —— 也可能是"修改意图应走 `modify_param` 分支覆写"而它没生效。

### 5.2 逐层参数进不了解析后的 IR

**现象**：程序侧已支持 `[0.3, 0.2]` 这种逐层输入（见优化记录），但 LLM 抽不出来 ——
IR 输出格式里没有逐层槽位与 few-shot 示例。所以**用户的提示词即使逐层写了，也到不了程序**。

**位置**：`app/llm_agent/prompt_templates.py`（IR 输出格式）、`app/knowledge/param_guide.py`

**待定**：给 `porosity` / `al` / `trpt` / `trpv` 补逐层写法示例，并说明"用户分层给就要分层填"。
