## 二、LLM 上下文记忆丢失

### 2.1 问题描述

用户反映 LLM "很傻，记不住上下文，说了下句上一句就忘了"。

### 2.2 根因分析

`intent_parser.py` 中的三个 LLM 调用——`classify_intent()`、`extract_entities()`、`generate_json_ir()`——每个都是**无状态单条消息**。对话历史存储在 `DialogueManager.state["history"]` 中，但从未传递给 LLM 的 prompt。LLM 每轮只能看到当前用户输入，完全不知道前几轮讨论过的内容。

虽然 `_merge_ir()` 在代码层面保留了前轮的 JSON IR 参数，但 LLM 本身在生成响应和提取新实体时，**缺乏对之前对话内容的语义理解**。

### 2.3 修复方案

**修改 3 个 Prompt 模板**，添加 `{conversation_history}` 占位符：

- `INTENT_CLASSIFICATION_PROMPT` — 意图分类时携带对话历史
- `NER_EXTRACTION_PROMPT` — 实体提取时携带对话历史（提示 LLM 结合历史一起提取）
- `IR_GENERATION_PROMPT` — IR 生成时携带对话历史

**新增方法** `DialogueManager._format_history_for_llm()`：

```python
def _format_history_for_llm(self) -> str:
    """格式化对话历史，最近10轮（20条消息），不截断内容"""
    history = self.state.get("history", [])
    if not history:
        return "（这是对话的第一轮，没有历史记录）"
    recent = history[-20:]
    lines = [f"共 {len(history)} 条历史消息，以下是最近 {len(recent)} 条："]
    for i, msg in enumerate(recent):
        role = "👤用户" if msg["role"] == "user" else "🤖系统"
        content = str(msg.get("content", ""))
        lines.append(f"[{i+1}] {role}: {content}")
    return "\n".join(lines)
```

**修改 `parse()` 调用链**：

```
DialogManager.process()
  → _format_history_for_llm()
  → IntentParser.parse(conversation_history=...)
    → classify_intent(conversation_history=...)
    → extract_entities(conversation_history=...)
    → generate_json_ir(conversation_history=...)
```

**修改文件**：
- `app/llm_agent/prompt_templates.py` — 3 个 prompt 添加历史占位符
- `app/llm_agent/intent_parser.py` — 全线传递 conversation_history 参数
- `app/llm_agent/dialogue_manager.py` — 新增 `_format_history_for_llm()`

## 三、边界条件录入失败

### 3.1 问题描述

用户描述的边界条件（如"西侧定水头100m，东侧定水头95m"）始终无法被正确录入模型。用户反复描述后系统仍显示 boundary_conditions 缺失。

### 3.2 根因分析

**三层缺陷叠加**：

1. **NER 提取不完整**（`prompt_templates.py`）：旧版 NER prompt 只提取 `boundary_type`（如"chd"），丢失了**位置**（西侧/东侧）和**数值**（100m/95m）信息。

2. **`normalize_entities()` 产出模糊**（`intent_parser.py`）：边界实体被转换为 `_boundary_hint: {type: "chd"}`，仅含类型不含位置和参数。

3. **LLM 收到不完整信息**：`IR_GENERATION_PROMPT` 收到的 `_boundary_hint` 没有足够信息构建完整边界结构。

### 3.3 修复方案

**Step 1 — 增强 NER prompt**：

新增 `boundary_condition_full` 实体类型，要求 LLM 提取：
- `position`: west/east/north/south
- `bc_type`: chd/ghb/wel/riv/drn
- `head_value`: 定水头值
- `stage_value`: 河流水位值
- `rate_value`: 井流量值

示例格式：
```json
{"entity_type": "boundary_condition_full", "position": "west", "bc_type": "chd", "head_value": 100, "unit": "m"}
```

**Step 2 — `normalize_entities()` 完整构建边界条目**：

```python
elif etype == "boundary_condition_full":
    bc_entry = {
        "type": bc_type,
        "name": f"{position}_boundary",
        "position": position,
        "parameters": {"head": {"value": float(head_val), ...}},
        "geometry": {"type": "edge", "position": position},
    }
    normalized[f"_boundary_entry_{idx}"] = {"value": bc_entry, ...}
```

**Step 3 — `_patch_json_ir()` 边界列表去重合并**：

收集所有 `_boundary_entry_*` 键，按 position 去重后写入 `ir["boundary_conditions"]`。

**Step 4 — FloPy 模型侧自动推断网格索引**：

`model_mapper._infer_edge_indices()` 已从边界名称（含"west"/"西"等关键词）自动推断网格边界 IJ 索引，无需 LLM 生成 grid_indices。

### 3.4 默认边界规则

针对用户未明确指定的边界：

| 边界位置 | 默认行为 | MODFLOW 实现 |
|----------|----------|-------------|
| 上边界（地表） | 自由水面 | 非承压含水层自动计算水位 |
| 下边界 | 隔水边界 | MODFLOW 默认 no-flow |
| 未指定的侧边界 | 零流量边界 | MODFLOW 默认 no-flow |

`_summarize_progress()` 在检测到部分侧面未指定时，自动提示默认行为。

**修改文件**：
- `app/llm_agent/prompt_templates.py` — NER prompt 新增 boundary_condition_full
- `app/llm_agent/intent_parser.py` — normalize_entities + _patch_json_ir 边界处理
- `app/llm_agent/dialogue_manager.py` — 进度摘要提示默认边界
- `app/modeling/model_mapper.py` — `_infer_edge_indices()` 边界位置推断

## 四、SQLite 线程安全问题

### 4.1 问题描述

Gradio 6.x 的 callback 运行在 worker 线程池中（非主线程），导致 SQLite 访问崩溃。

### 4.2 错误信息

```
SQLite objects created in a thread can only be used in that same thread.
```

### 4.3 修复

```python
# app/knowledge/semantic_db.py
self._lock = threading.Lock()
self.conn = sqlite3.connect(db_path, check_same_thread=False)

def _execute(self, sql, params=None):
    """线程安全的 SQL 执行"""
    with self._lock:
        cursor = self.conn.cursor()
        if params:
            cursor.execute(sql, params)
        else:
            cursor.execute(sql)
        return cursor
```

所有 `self.conn.execute()` 替换为 `self._execute()`。

## 五、自然语言 → 参数传递链路修复

### 5.1 多轮防御策略

经过多轮调试，建立了**三层防御**确保参数不丢失：

| 层级 | 机制 | 作用 |
|------|------|------|
| 防御 1 | `_patch_json_ir()` 预写入 | 将 NER 可靠提取的参数直接写入 IR |
| 防御 2 | `_patch_json_ir()` 再写入 | LLM 生成后重新应用（防止 LLM 丢弃） |
| 防御 3 | `_merge_ir(patched_ir, json_ir)` | 深度合并：base 非空值优先保留 |

### 5.2 `_merge_ir()` 关键修复

**Bug**：旧版 merge 逻辑中，空值 base 覆盖了 LLM 的正确值。

**修复**：新增 `_is_empty()` 静态检查，只有 base 非空时才保留 base 值：

```python
@staticmethod
def _is_empty(val) -> bool:
    if val is None: return True
    if isinstance(val, str) and not val.strip(): return True
    if isinstance(val, (list, dict)) and len(val) == 0: return True
    return False
```

### 5.3 参数传递完整链路

```
用户输入
  → classify_intent()          ← 带对话历史
  → extract_entities()         ← 带对话历史 + 当前 IR
  → normalize_entities()       ← 处理 9 种实体类型（含 boundary_condition_full）
  → _patch_json_ir()           ← 防御1: 直接写入，含边界去重合并
  → generate_json_ir()         ← 带对话历史 + patched IR
  → _patch_json_ir() 再应用    ← 防御2: LLM输出后再写入
  → _merge_ir(patched, llm)    ← 防御3: 保留所有历史非空值
  → detect_missing_params()
```

## 十、对话上下文窗口扩大（2026-06-17）

### 10.1 问题

原有 `_format_history_for_llm()` 保留最近 20 条消息（约10轮），`_build_context_str()` 仅保留 6 条（约3轮）。对于复杂建模场景，用户可能需要 10+ 轮对话才能完整描述模型参数，过小的上下文窗口导致 LLM 丢失早期讨论内容。

### 10.2 调整

| 方法 | 旧值 | 新值 | 说明 |
|------|------|------|------|
| `_format_history_for_llm()` | `history[-20:]` (~10轮) | `history[-40:]` (~20轮) | 传递给 LLM 的对话上下文 |
| `_build_context_str()` | `history[-6:]` (~3轮) | `history[-20:]` (~10轮) | 问题生成等场景的上下文 |

DeepSeek v4 上下文窗口足够大，40 条消息不会超出限制。

**修改文件**：`app/llm_agent/dialogue_manager.py`

## 十一、FloPy 建模子系统调试（2026-06-17）

**调试依据**：[调试方案-202606.md](../调试方案-202606.md) 的 Span 6-10 + L2 边界对验证

### 11.1 IMS 求解器不收敛（Span 7）

**现象**：`test_model_builder.py` 中 AutoModelBuilder 构建的模型运行 MODFLOW 6 时报：
```
FAILED TO MEET SOLVER CONVERGENCE CRITERIA IN TIME STEP 1 OF STRESS PERIOD 1
```
而相同参数的 `flopy_baseline_test.py` 正常收敛。

**根因**：AutoModelBuilder 生成的 `.ims` 文件中 `INNER_DVCLOSE=0.001`，远松于 `OUTER_DVCLOSE=1e-5`。线性求解器每次只做1次内迭代就退出，非线性外迭代永远收敛不到1e-5。

**修复**：
- `app/modeling/model_builder.py` `_build_solver()`：`rclose` 未指定时自动设为 `outer_dvclose / 10`，并添加安全检查
- `app/modeling/model_mapper.py` `map_solver_params()`：`rclose` 不再有硬编码默认值 `1e-3`，仅在用户显式指定时传递

### 11.2 边界位置推断误匹配（Span 6）

**现象**：`_infer_edge_indices()` 使用单字符关键词 `"w"`, `"e"`, `"n"`, `"s"` 导致：
- `"center_well"` 含 `w` → 误判为west边界
- `"south_boundary"` 含 `n` → 误判为north
- `"northeast_corner"` 含 `"east"` → 误判为east

**修复**：
- 移除单字符关键词，添加单词边界检查函数 `_word_match()`
- 对中文关键词使用简单子串匹配（`isalpha()` 对中文字符返回 True）

### 11.3 各向异性参数计算错误（Span 6）

**现象**：`hani`（Kh/Kv 比）转换为 `vka`（Kv）时使用了乘法 `hk * hani`，实际应为除法 `hk / hani`。

**修复**：`map_aquifer_params()` 中将 `hk_v * hani_v` 改为 `hk_v / hani_v`。

### 11.4 DRY_CELLS 复数形式未识别（Span 8）

**现象**：`_classify_error()` 只检查单数 `"cell went dry"`，MODFLOW 6 实际输出复数。

**修复**：改为检查 `"went dry"` 覆盖单复数。

### 11.5 NON_CONVERGENCE 错误分类增强

**现象**：MODFLOW 6 输出 `"FAILED TO MEET SOLVER CONVERGENCE CRITERIA"` 既不包含 `"did not converge"` 也不包含 `"failed to converge"` 子串，被误判为 UNKNOWN。

**修复**：增加组合匹配 `"failed" in text AND "converge" in text`。

### 11.6 RCH 面状补给包兼容性

**问题**：FloPy 3.10 的 `ModflowGwfrch` 不接受以前版本兼容的 `stress_period_data` 格式（标量/ndarray/dict-of-ndarray 均报错）。

**处理**：标记为已知 FloPy 3.10 API 问题，RCH 包创建暂时跳过，待后续适配。

### 11.7 GWT SSM 源汇项格式

**问题**：`ModflowGwtssm(gwt, sources={0: []})` 在 FloPy 3.10 中报格式错误。

**修复**：改为 `sources=None`（无额外质量源时）。

## 十四、溶质运移（GWT）链路调试（2026-09-17）

### 14.0 触发问题

East Texas 填埋场渗滤液运移案例的运行结果"**像水流模型结果**"——污染羽占满整个含水层、
呈北高南低的梯度，而不是从 `landfill` 区域持续泄漏的点源。用户问：这是提示词问题还是
程序问题？同时报出两处现象：方位上下颠倒、模拟时长仍显示 150000 天。

**结论：全是程序缺陷，提示词无责。** LLM 产出的 IR 是正确的：

```json
{"type": "rch", "name": "landfill_boundary", "position": "landfill",
 "parameters": {"rate": 1e-4, "concentration": 20000}}
```

问题全部出在消费这份 IR 的代码上，共四处，彼此独立。

### 14.1 点源被静默放大成全域（170 倍）

旧代码分三步丢掉了源区定位：

| 环节 | 行为 |
|------|------|
| `model_mapper` | 只读 `bc["geometry"]["grid_indices"]`，而该 IR 没有这个键 |
| `_infer_edge_indices` | 只认 west/east/north/south 等方位词，`landfill` 一个都不匹配 → `[]` |
| 兜底分支 | `elif conc is not None:` → **把源项展开成 layer0 全网格**，只写一句到不了任何 UI 组件的 `logger.info` |

量化（103×218 网格，`delr = delc = 20 m`，单格 400 m²）：

| 量 | 缺陷态 | 正确态 | 倍数 |
|------|------|------|------|
| `.rch` 逐格记录 | 22454（= 103×218 全域） | **132** | 170.1× |
| 启用格子面积 | 8 981 600 m² | **52 800 m²** | 170.1× |
| 补给总量 | 898.16 m³/d | **5.28 m³/d** | 170.1× |

（填埋场多边形的真实面积实测 54 225 m²，与栅格化后的 52 800 m² 相差 2.6%，
是格子离散化的正常差异，不是错误。）

**为何整套验证都没抓到**：`verify_gwt_cases.py` 的 Case A/B 与 `verify_east_texas.py` 的
Case C **都在 IR 里显式给了 `geometry.grid_indices`**，走的是 mapper 优先级 1 的直接透传，
"从 `position` 名 + 上传 SHP 解析源区"这条链路**在验证套件里从未被执行过**。

**修法**：新建 `app/modeling/source_zone.py`，三级定位（IR `grid_indices` → IR
`coordinates`/`bbox` → 上传 SHP 名称匹配），全失败时**硬拒绝**（`SourceZoneUnresolved`），
绝不回落全网格。解析结果物化进 IR 的 `geometry.grid_indices`，因此 20 个 `build_and_run`
调用点、5 个 `build_simulation`、4 个 `map_boundary_conditions` 签名全部不变；原点提升为
IR 字段 `domain.origin_xy`（上传时由 `file_parse_handler` 写入）。

两处容易再踩的坑：

- 名称匹配必须**分词**，朴素的 `in` 会让 `top_of_landfill` 因 `north_keywords` 含 `"top"`
  命中整条北边界，也会让 `Aquifer Layer 1_polys` 里的 `1` 误命中；
- `infer_edge_indices` 对 `rch`/`evt`/`wel` 一律返回空 —— 整条边界的补给带或井排几乎
  不可能是本意，这类名称应交给源区解析器。

新增回归锁 `scripts/verify_east_texas.py` 的 **Case D**（`python scripts/verify_east_texas.py D`，
`ET_D_RUN=1` 再加跑 mf6），**不给 `grid_indices`**，直接断言写出来的 `.rch` 文件本身：
132 条记录、row 恰好 52..62、col 恰好 137..148、layer 0、合计 5.2800 m³/d。
有效性已验证（非同义反复）：把原点故意偏移 500 m 断言即红（rows 27..37 / cols 112..123），
偏移 20 m（恰好一格）时 col 断言仍红。

### 14.2 perlen 语义误解，总时长差 10 倍

`perlen` 按 MF6 原生语义是**单个应力期的长度**，不是总时长。IR 里
`{nper: 10, perlen: 15000}` 使总时长成为 10 × 15000 = **150000 d**，而提示词要的是 15000 d。

**修法**：新增一等公民字段 `stress_periods.total_time`（d），`perlen = total_time / nper`
由程序确定性算出，不再依赖 LLM 猜。优先级 `period_data` > `total_time` > 平铺 `perlen`
> 合成的 1.0。

同一条链上还有三个独立缺陷，一并修掉：

1. **`_merge_ir` 的白名单在每一层递归都生效**。`VALID_TOP_KEYS` 装的是 `project`/`grid`/
   `stress_periods` 这类**顶层**键名，套到每层递归上会把所有嵌套键判成"非标准键"丢弃 ——
   实测 `{nper:10, steady_state:false, total_time:15000, nstp:1}` 被砍成 `{"nper":10}`，
   `total_time` 静默消失。修为白名单只在 `_depth == 0` 生效。
2. **`PARAM_PATH_MAP` 把 `nper` 映射到父路径 `stress_periods`**，NER 抽到的
   `stress_periods = 10` 于是被写成**裸标量**，覆盖掉 LLM 产出的正确 dict。改为落到
   `stress_periods.<子字段>`，并补 `time_steps_per_stress_period` → `stress_periods.nstp`
   （原先会落到语义完全无关的 `aquifer.parameters.*`）；同时在 `_patch_json_ir` 增加
   标量/列表/字符串形态的归一化与告警。
3. **校验层对"总时长差 10 倍"完全瞎掉**。`stress_periods` 有六种实际形态
   （dict / 平铺 perlen / 裸整数 10 / 字符串 / 单元素列表 / 垃圾值），`validator` 里
   既没有归一化、也**从不遍历 `stress_periods`**（只往 `PHYSICAL_RANGES` 加字典条目是
   空操作）。`_check_pre_run` 还会直接崩：`stress.get("nper")` 撞上裸整数 `10` →
   `AttributeError`。修法：唯一实现在 `app/utils/ir_normalize.py`
   （`normalize_stress_periods` / `merge_time_sources`；`physics_engine` 不能 import
   `modeling`，故放 `app/utils/`），校验层补遍历块 + `_check_time_discretization`
   （`total_time` 与 `period_data` 冲突 > 1% → ERROR；总时长 > 1e5 d 且启用运移 → WARNING，
   长时段模拟本身合法，不能阻断）。

### 14.3 方位名与网格行方向上下颠倒

仓库里同时存在两套相反的行方向约定，单独看各自自洽，放一起就是"名为 `north` 的边界被
写到最南一排、画在图的底部"：

| 位置 | 修复前 | 修复后 |
|------|------|------|
| `app/modeling/source_zone.py` `infer_edge_indices` | `north` → **row 0** | `north` → row nrow-1 |
| `app/utils/grid_coords.py` `grid_cell_centers`（未改） | row 索引随 y 增大 ⇒ row 0 在图最下方 | 同左 |

**证据链（实测，非推理）**：

- 会话 IR 的 `south_boundary` 是 GHB stage 212，写进 `auto_model_gwf.ghb` 的记录是
  `1 103 <col> 212 ...`（1-based row 103 = 0-based 102 = nrow-1）；
- 读 09/15 那次运行的 `.hds` 末帧：最高水头 211.997 在 (row 102, col 0)，最低 208.019
  在 (row 0, col 217)，与边界赋值吻合；
- 绘图链路 `contourf(X, Y, head)` 全链路**没有任何翻转/转置**
  （`flipud` / `np.flip` / `[::-1]` 在 `app/` 下 grep 零命中），故 row 102 落在图的上方。

**为什么改 `infer_edge_indices` 而不是改 `grid_cell_centers`**：判据是与 SHP 独立对齐。
`landfill_arcs` 在 y 上占 (3428453−3427412)/1871 = **55.6%**，栅格化后正是 rows 52..62
（中心 55%）——只有"row 越大越靠北"这一套能同时对上 SHP 坐标、可视化底图和 `.rch` 的
实测行号；改 `grid_cell_centers` 会把已经对齐 SHP 的底图整体镜像。

统一为：**row 0 在南、row nrow-1 在北；col 0 在西、col ncol-1 在东**（即"上北下南"）。

回归锁见 `tests/test_source_zone.py` 的 5.9a~5.9f —— 关键不是"north → nrow-1"这一条，
而是 5.9e/5.9f：把两套约定钉在一起断言 `y(row nrow-1) > y(row 0)`、`x(col 0) < x(col ncol-1)`。
单看任何一套都自洽，只有这种跨模块不变量能挡住它们再次漂移。**这个 bug 能存活就是因为
它没有任何测试**。修后 `test_subsystem_integration` 由 89/90 转为 90/90。

## 十五、单时刻污染羽：色标上下限改为「确定重绘」（2026-09-17）

### 15.0 触发问题

> "为什么我输入浓度下限或上限的时候每输入一个数，系统就要自动运算一下呢？例如，我想在
> 浓度下限框输入 '300'，但我在输入 '3' 以后程序就已经开始自动运行了，我只有在程序刷新出
> 3 的结果以后才能再输入一个 '0'。我想可以直接设置一个'确定'按钮。"

### 15.1 根因：事件语义，不是计算慢

`gr.Number.change` 是**逐字符**触发的 —— 每敲一个键就是一次完整重绘。这不是性能问题，
改快也没用：用户键入 `300` 需要三次击键，中间两次都会打断输入。

原接线（`app/frontend/gradio_app.py`）：

```python
for _w in (plume_auto_range, plume_vmin, plume_vmax):
    _w.change(_on_plume_number,
              [plume_time_num, plume_auto_range, plume_vmin, plume_vmax, sid_state],
              [plume_single_plot, plume_status, plume_time_slider, plume_vmin, plume_vmax])
```

三个控件里，只有复选框的 `change` 是合理的（单击一次即生效，不涉及键入）。

### 15.2 改法

新增 `✅ 确定重绘` 按钮与处理器 `_on_plume_apply(slider_t, num_t, auto_range, vmin_in,
vmax_in, sid)`，接线收敛为：

| 触发源 | 事件 | 说明 |
|---|---|---|
| `plume_time_slider` | `release` | 拖动结束才触发（原样保留） |
| `plume_time_num` | `submit` | 回车即改（原样保留） |
| `plume_apply_btn` | `click` | **新增**：输入完上下限再点 |
| `plume_vmin` / `plume_vmax` | `submit` | **新增**：回车等价于点确定 |
| `plume_auto_range` | `change` | 复选框单击一次即生效 |

要点：

- 处理器**复用** `_render_plume`，不复制逻辑 → 色标解析的既有语义（勾自动忽略输入框、
  单框留空回退自动、上限小于下限自动纠正）一并继承。
- 时刻取值：数字框有有效值用它，否则回退滑块位置（`release` 本就会把滑块位置回写进数字框，
  两者始终同步）。
- 顺带消除一类隐患：程序回写输入框不再引发新事件，**不存在回环**。
- 两个框的 `info=` 文案与 `plume_status` 初始文案都改为明示"点确定重绘或按回车"。

### 15.3 回归锁：断言"组件图上的边"
