### 2026-10-10 · 修：GWT 链路支持逐层孔隙度 / 弥散度（开发计划第 1 项）

**问题**：提示词逐层给参数（「第一层：孔隙度0.3，纵向弥散度20m……第二层：孔隙度0.2，纵向弥散度20m……」），
程序只取**一个**值，分层信息被静默丢弃。East Texas 实测：`porosity CONSTANT 0.20000000`、
`alh CONSTANT 40.0`。第 1 层真实孔隙度 0.3 却按 0.2 算 —— 孔隙度越小流速越大，等于把第 1 层运移速度算偏快。

**改动**：

| 文件 | 改了什么 |
|---|---|
| `app/modeling/model_builder.py` | 新增模块级 `_to_layer_array(value, nlay, nrow, ncol, name)`；`_build_gwt` 的 MST 孔隙度与 DSP 的 `alh` 改走它 |
| `app/physics_engine/constraints.py` | `check_json_ir_params` 里新增 `_emit()`，逐层序列拆成 `porosity[层1]`/`porosity[层2]` 多条结果（`dataclasses.replace` 改名，范围查询仍按原名） |
| `app/physics_engine/validator.py` | 新增 `_as_float_any()`（序列取均值）；改 `_check_physics` 的达西/Pe 数取数与 `_check_stability` 的 Courant 取数；顺手修掉 `aqua.get("hk", {}).get("value")` 遇裸数字会抛 `AttributeError` 的坑 |
| `app/analysis/process_identifier.py` | 参数提取加 `_num()`，逐层取均值（`max(porosity, 0.01)` 传列表会直接抛） |
| `app/frontend/gradio_app.py` | `_extract_process_params` 加 `_num()`；**并修正它此前只从 `transport` 顶层读 `al`** —— `al` 实际写在 `transport.dispersion.al`，等于每次都落回 `al=10.0` 默认值；孔隙度补 `aquifer.parameters` 兜底 |
| `tests/test_per_layer_transport.py` | 新建，21 项回归锁 |
| `tests/test_model_builder.py` | 5a 断言由 1 条提示改为 2 条，新增 5a' 反例 |

**为什么这么改**：
- **标量输入必须原样透传，不能统一展成数组。** FloPy 对标量写 `CONSTANT`、对长度 nlay 的序列写 `LAYERED`；统一展平会改掉 East Texas 等既有案例的基线。测试 2b 专门锁这一点。
- 逐层长度必须等于 `nlay`，否则 `ValueError`（消息带 nlay）—— 长度对不上时静默取第一个是最坏选择。
- 校验层不能"看起来查过了"。修复前 `check_json_ir_params` 对列表值会走「无法转换为数值，跳过范围检查」的 INFO 分支，**一个值都没查**。
- 已有 `porosity=0.3/0.9` 这类越界值现在会被逐层抓出（测试第 4 节）。

**验证**：
- `python tests/test_per_layer_transport.py` → **21/21 通过**。关键断言：文件里 `porosity LAYERED`、`alh/ath1/atv LAYERED`；`diffc` 仍 `CONSTANT`（标量不被误展）；0.3 在 0.2 **之前**写出（防写倒层）；标量输入仍是 `porosity CONSTANT 0.20000000`。
- 回归全绿：`test_gwt_pipeline` 52/52、`test_model_builder` 全部、`test_boundary_pairs` 全部、`test_error_handling` 23/23、`test_subsystem_integration` **90/90**（基线是 89/90）、`test_analysis_import` 全部、`test_all_imports` 30/31（与既有基线一致，非本轮引入）。

**影响**：逐层介质的溶质运移速度不再算错。标量案例零影响（基线不变）。

### 2026-10-10 · 修：运移参数来源送到界面（开发计划第 2 项）

**问题（诊断与计划里的初判不同，此处据实修正）**：计划里写的是「用户给了 20 m，却没进 IR，
于是落到 `2×网格尺寸` 的默认值分支」。**实际情况不是这样** —— 查 `data/sessions/default.json`
与对话历史后确认：

- IR 里 `transport.dispersion.al = 40`，且标着 `"source": "user_input"`。**不是**默认值分支产生的。
- 40 另有出处：用户此前还发过**另一套**提示词（「单层网格 103 行×218 列……纵向弥散度 **40m**、
  横向比 0.1、垂向比 0.01」）。IR 是两套提示词的**混合残留** —— `al`/`trpt`/`trpv` 停在旧值上，
  `porosity` 被压成单值 0.2。
- 而「40」恰好也等于 `2×20 m`，两条路径同值，把问题掩盖得更彻底。

**所以真正的缺陷是**：程序**从不告诉用户它实际用了什么值**。用户改了提示词、IR 却停在旧值上，
界面上没有任何地方能发现"我写的和它用的不是一回事"。

**改动**：

| 文件 | 改了什么 |
|---|---|
| `app/modeling/model_mapper.py` | `map_transport_params` 记录 `al_source`（`"ir"` / `"grid_default"`）与 `porosity_source`（`"transport"` / `"aquifer"`） |
| `app/modeling/model_builder.py` | `_build_gwt` 把实际写入的运移参数存进 `self._effective_transport`；走 `grid_default` 时调 `_warn()`（该通道已能进界面）；`build_and_run` 返回值新增 `transport_effective`；`build_simulation` 里复位 |
| `app/frontend/gradio_app.py` | 新增 `_effective_transport_text()`；结果摘要的 telemetry 行增加「运移参数（实际写入模型）」 |

**为什么这么改**：不试图猜 LLM 为什么留着旧值（那是抽取链路，不可确定性修复），
而是**让实际生效的值当场可见**。走默认值时额外给一条不阻断的提示。

**验证**：
- 新增断言在 `tests/test_per_layer_transport.py` 第 3 节：显式给 `al` → `al_source="ir"`；
  不给 → `al_source="grid_default"` 且值 = 40（`2Δx`，Péclet≈0.5 的稳定取法）。
- `tests/test_model_builder.py` 5a/5a' 锁住「没给 al 就提示、给了 al 就不提示」。
- 渲染实测：逐层 → `αL=逐层 20/20 m（输入）｜n=逐层 0.3/0.2（aquifer 段）｜…`；
  走默认 → `αL=40 m（默认(网格尺度)）｜…`。

**影响**：**不改变任何计算结果**，只增加可见性。East Texas 的 `al=40` 来源现在写明白了。

### 2026-10-10 · 结：UI 里 `gr.Plot` 画不出图**不是程序缺陷**（开发计划第 3 项，关闭）

**结论**：**是我那个截图工具的注入路径问题，不是程序缺陷。** 真实 UI 的接线本来是对的。

**证据**：把 `scripts/_ui_shot_make.py` 的注入从「19 个输出混在一个 `demo.load` 里」
改成**三组**、每组镜像真实 UI 的一个 handler 之后，三个图 tab **全部正常渲染**：

| Tab | 渲染结果 |
|---|---|
| 水头分布 | `data:image/webp;base64`，1500×1050 |
| 污染羽 | 2025×1140（总览）+ 1350×975（单时刻） |
| 过程分析 | 1950×900 |

三处 `loading` 元素计数均为 **0**。

**为什么会误判**：真实用户走 `run_btn.click(run_model_handler, ...)` → **7 个输出**，
再接 `.then(_sync_plume_controls, ...)` → **6 个输出**（`gradio_app.py` 的接线）；
我那个工具图省事，把 `file_parse_handler` / 会话状态等一共 19 个输出塞进**一个** `demo.load`。
两条路径不同，出问题的是工具那条。

**改动**：`scripts/_ui_shot_make.py` 的 `OUT_IDS` 拆成 `RESULT_IDS`（7）/ `PLUME_IDS`（6）/
`INPUT_IDS`（6），对应三个独立的 `demo.load`。

**验证**：见上表；`python scripts/_ui_shot_take.py --probe --click 水头分布` 即可复现。

**影响**：开发计划第 4 项（报告图 1–6 重做）的**阻塞已解除** —— 工具现在能正常出图。
但按 2026-10-10「不再同步更新报告」的决定，该项仍按技术债挂着，不主动推进。
