### 2026-10-10 · 修：反应运移（吸附 / 一级降解）真的写进模型（开发计划板块二）

**问题**：反应参数**一直被读、被校验，然后被静默丢弃**。

`map_transport_params`（`model_mapper.py:520` 一带）早就把 `sorption` / `kd` / `decay_type` /
`decay_rate` 抽出来放进了返回 dict；`constraints.check_json_ir_params` 也会去查它们的范围；
`intent_parser` 甚至把它们接到了 IR 路径上。但 `_build_gwt` **从头到尾没有读过这些键** ——
建出来的模型没有任何反应，界面上也没有任何地方能发现。用户写了 Kd、写了半衰期，
拿到的仍然是一条既不吸附也不降解的羽流。

**改动**：

| 文件 | 改了什么 |
|---|---|
| `app/modeling/model_mapper.py` | `map_transport_params` 的反应块重写：完整提取 `sorption`（归一化 + 白名单，非法值 `warn` 后按 `none`）、`kd`（兼容 `distcoef` 别名）、`bulk_density`（兼容 `rho_bulk`）、`sp2`、`decay_type`、`decay_rate`（`first_order_rate` 优先，否则由 `half_life` 按 λ=ln2/t½ 换算，带 `decay_rate_source`）；新增 `import math` |
| `app/modeling/model_builder.py` | 新增 `_reaction_mst_options()`：把反应写成 **MST6** 选项（`SORPTION` / `FIRST_ORDER_DECAY` + `DISTCOEF` / `BULK_DENSITY` / `DECAY` / `DECAY_SORBED`），含 L/kg→m³/kg、kg/L→kg/m³ 的单位换算与阻滞因子计算；新增 `self._effective_reaction`，随 `build_and_run` 返回值（成功/失败两条路径都带）送出 |
| `app/physics_engine/constraints.py` | `PHYSICAL_RANGES` 补 `first_order_rate` / `half_life` / `bulk_density`；`check_json_ir_params` 的 `transport.reaction` 遍历重写（原来 kd 检查误写在 `for sub_key in ("decay",)` 循环体内，靠"元组恰好只有一个元素"碰对） |
| `app/frontend/gradio_app.py` | 新增 `_effective_reaction_text()`；结果摘要 telemetry 增加「反应参数（实际写入模型）」行 |
| `app/llm_agent/prompt_templates.py` | IR 输出格式补 `transport` 块（含 `reaction`）；补中文填写规则（只在用户提及时写、kd 单位 L/kg、ρb 单位 kg/L、t½ 不要自行换算、逐层写数组） |
| `app/llm_agent/intent_parser.py` | `KNOWN_PARAM_PATHS` 与参数映射补 `sorption` / `bulk_density` / `decay.type` / `half_life` / `kd` |
| `app/knowledge/param_guide.py` | 补 6 条反应参数说明（`_range_text()` 从 `PHYSICAL_RANGES` 派生，不复制） |
| `docs/ir_schema_v1.0.json` | 补 `transport.porosity`、`reaction.bulk_density`、`reaction.sp2` 及各字段 `description` |
| `tests/test_reaction_transport.py` | 新建，23 项回归锁（含 MF6 6.3.0 端到端） |

**为什么这么改**：

- **反应写在 `MST6`，不是 `IST6`。** 计划原文写的是「`ModflowGwtist` 接入」，**方向是错的**。
  MF6 的 **IST6 是 "Immobile Storage and Transfer" —— 双域（mobile–immobile）包**。
  按计划建 `ModflowGwtist` 后，MF6 6.3.0 直接硬报
  `DUAL DOMAIN IS ACTIVE BUT ZETAIM WAS NOT SPECIFIED`，必须再补 `THETAIM`/`ZETAIM`
  两个**假想的非移动域参数**才能跑 —— 那就把单域模型悄悄改成了双域模型。
  把 IST6 的 dfn 定义与 `ModflowGwtmst.__init__` 的签名对照后确认：**反应（吸附 + 降解）属于 MST6**，
  而项目**本来就构建了 MST6**（只是调用时没传反应参数）。
- **`half_life` 这条路径从来没有接线。** IR schema、校验器、提示词都提到了半衰期，
  但 `map_transport_params` 只读 `first_order_rate` —— 用户给半衰期等于什么都没给。
  现已按 λ = ln2/t½ 换算（放在程序里做，不交给 LLM：LLM 换算既不透明也无从核对）。
- **`first_order_rate` / `half_life` 不在 `PHYSICAL_RANGES` 里。** `check_param` 落到
  「不在已知物理范围表中，默认通过」的 INFO 分支 —— **看起来查过了，一个值都没查**，
  与板块一 porosity 逐层那次是同一类空转。现已补上范围条目（t½ 的上下界就是 λ 的倒数）。
- **单位陷阱（1000 倍）**：IR 惯用 Kd = L/kg、ρb = kg/L；MF6 的 `DISTCOEF` 要 **m³/kg**、
  `BULK_DENSITY` 要 **kg/m³**。这两个单位在数值上互为倒数（乘积无量纲），
  所以**直接填文献值，阻滞因子 R 看着是对的，但吸附相浓度会差 1000 倍**。
  转换常量：`_KD_L_PER_KG_TO_M3_PER_KG = 1e-3`、`_RHOB_KG_PER_L_TO_KG_PER_M3 = 1e3`。
- **吸附与降解同时启用时必须给 `DECAY_SORBED`**，否则 MF6 硬报
  `DECAY_SORBED not provided in GRIDDATA block but decay and sorption are active.`。
  **取 0 是有依据的**：令 λ_sorbed = 0 时总方程恰好退化为经典（与 MT3DMS 同源）形式
  `R·∂C/∂t = ∇·(D∇C) − v·∂C/∂x − λC`；若取 λ_sorbed = λ，等效衰减率会变成 λR，与解析解对不上。
  同时给一条提示，让用户知道这个值不是我们瞎填的。
- **说了要反应却给不出参数时必须说出来**：「启用吸附但没给 Kd」「启用降解但 λ/t½ 都没有」
  不静默按无反应建包，而是留下可展示的警告。

**验证**：

### 2026-10-10 · 修：运移参数来源送到界面（开发计划第 2 项）

**问题（诊断与计划里的初判不同，此处据实修正）**：计划里写的是「用户给了 20 m，却没进 IR，
于是落到 `2×网格尺寸` 的默认值分支」。**实际情况不是这样** —— 查 `data/sessions/default.json`
与对话历史后确认：

- IR 里 `transport.dispersion.al = 40`，且标着 `"source": "user_input"`。**不是**默认值分支产生的。
- 40 另有出处：用户此前还发过**另一套**提示词（「单层网格 103 行×218 列……纵向弥散度 **40m**、
  横向比 0.1、垂向比 0.01」）。IR 是两套提示词的**混合残留** —— `al`/`trpt`/`trpv` 停在旧值上，
  `porosity` 被压成单值 0.2。
- 而「40」恰好也等于 `2×20 m`，两条路径同值，把问题掩盖得更彻底。

**所以真正的缺陷是**：程序**从不告诉用户它实际用了什么值**。用户改了提示词、IR 却停在旧值上，
界面上没有任何地方能发现"我写的和它用的不是一回事"。

**改动**：

| 文件 | 改了什么 |
|---|---|
| `app/modeling/model_mapper.py` | `map_transport_params` 记录 `al_source`（`"ir"` / `"grid_default"`）与 `porosity_source`（`"transport"` / `"aquifer"`） |
| `app/modeling/model_builder.py` | `_build_gwt` 把实际写入的运移参数存进 `self._effective_transport`；走 `grid_default` 时调 `_warn()`（该通道已能进界面）；`build_and_run` 返回值新增 `transport_effective`；`build_simulation` 里复位 |
| `app/frontend/gradio_app.py` | 新增 `_effective_transport_text()`；结果摘要的 telemetry 行增加「运移参数（实际写入模型）」 |

**为什么这么改**：不试图猜 LLM 为什么留着旧值（那是抽取链路，不可确定性修复），
而是**让实际生效的值当场可见**。走默认值时额外给一条不阻断的提示。

**验证**：
- 新增断言在 `tests/test_per_layer_transport.py` 第 3 节：显式给 `al` → `al_source="ir"`；
  不给 → `al_source="grid_default"` 且值 = 40（`2Δx`，Péclet≈0.5 的稳定取法）。
- `tests/test_model_builder.py` 5a/5a' 锁住「没给 al 就提示、给了 al 就不提示」。
- 渲染实测：逐层 → `αL=逐层 20/20 m（输入）｜n=逐层 0.3/0.2（aquifer 段）｜…`；
  走默认 → `αL=40 m（默认(网格尺度)）｜…`。

**影响**：**不改变任何计算结果**，只增加可见性。East Texas 的 `al=40` 来源现在写明白了。

### 2026-10-10 · 结：UI 里 `gr.Plot` 画不出图**不是程序缺陷**（开发计划第 3 项，关闭）

**结论**：**是我那个截图工具的注入路径问题，不是程序缺陷。** 真实 UI 的接线本来是对的。

**证据**：把 `scripts/_ui_shot_make.py` 的注入从「19 个输出混在一个 `demo.load` 里」
改成**三组**、每组镜像真实 UI 的一个 handler 之后，三个图 tab **全部正常渲染**：

| Tab | 渲染结果 |
|---|---|
| 水头分布 | `data:image/webp;base64`，1500×1050 |
| 污染羽 | 2025×1140（总览）+ 1350×975（单时刻） |
| 过程分析 | 1950×900 |

三处 `loading` 元素计数均为 **0**。
